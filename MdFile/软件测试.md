### 一、软件测试是什么
一句话定义：**验证软件是否满足需求，并尽早发现缺陷（bug）的过程。**
关键理解：
- 测试不是"找茬挑刺"，而是**验证软件该不该这么干、能不能正常干**
- 核心动作：给软件输入 → 看实际结果 → 对比"预期结果"，不一致就是bug

必记4个名词（今天反复用）：
| 名词 | 意思 | 例子 |
|------|------|------|
| 需求（Requirement）| 软件应该做到什么 | 登录页要求账号6~12位字母数字 |
| 预期结果 | 按需求，应该出现什么 | 正确输入后能跳转首页 |
| 实际结果 | 程序真实跑出来的 | 正确输入却报"账号错误" |
| 缺陷（Bug） | 实际≠预期 | 上面就是bug |

### 二、测试阶段划分
软件从开发到上线，测试按顺序分4个阶段：
1. **单元测试**：测单个代码模块（比如"计算函数"单独测）
2. **集成测试**：多个模块拼起来测（登录+权限模块连起来）
3. **系统测试**：整个软件整体测（把整个APP当黑盒，按需求逐项验）
4. **验收测试**：给用户/客户最后确认"能不能交付"
> 你以后做的是**系统测试+集成测试**为主，单元测试偏开发。

### 三、测试方式分类
按"是否看代码"分两类：
- **黑盒测试**：不关心内部代码，只看输入输出对不对（像用遥控器，不用懂内部线路）
- **白盒测试**：要看源代码，检查逻辑、分支、条件有没有漏洞（像拆开机器看齿轮）
- 灰盒测试：介于两者之间，知道一部分内部结构

按"是否运行程序"分两类：
- **静态测试**：不运行程序，直接审查文档、看代码（评审需求、代码审查）
- **动态测试**：运行程序后操作验证（点按钮、输数据看结果）

> 记忆技巧：**黑盒=不看代码**、**白盒=看代码**；**静态=不运行**、**动态=运行**。

### 黑盒测试用例设计方法
1. 等价类划分法

把输入数据划分成**有效等价类、无效等价类**，同一类里面只选 1 个代表数据写用例，减少重复用例。

- 例子：密码要求 6~16 位
  - 有效等价类：8 位字符
  - 无效等价类：5 位、17 位、空输入
- 适用：输入框、参数校验（接口、表单）

2. 边界值分析法

**找输入范围的边界点**，边界最容易出 bug！经常配合等价类一起使用。

- 例子：密码 6~16 位
边界：5、6、16、17
- 口诀：**上点、内点、离点**
- 适用：有长度、数字范围限制的输入

3. 场景法（业务场景法）

按照**业务流程**，梳理主流程、备选流程、异常流程，基于业务场景写用例。

- 例子：电商下单：正常下单、库存不足下单、余额不足下单
- ✅**系统测试最常用**，测完整业务流程

4. 判定表法（决策表）

多输入条件组合，条件多、互相有制约关系，列出所有组合，生成用例。

- 例子：会员折扣：会员 + 满减、会员无满减、非会员 + 满减
- 适用：多条件组合判断的功能

5. 错误推测法（猜错法）

凭测试经验，猜容易出错的地方，直接设计用例。

- 例子：输入特殊符号、连续快速点击、空提交
- 特点：辅助方法，不单独用来写全部用例，用来补充用例

### 白盒测试用例设计方法（单元测试，开发为主）

1. **语句覆盖**：保证所有代码语句至少执行一次
2. **判定覆盖（分支覆盖）**：所有 if 判断的真假分支都走到
3. **条件覆盖**：判断里面每一个条件的真假都覆盖
4. **判定 - 条件覆盖**
5. **条件组合覆盖**
6. **路径覆盖**：覆盖程序所有执行路径

### 软件测试步骤

1. **测试前期：需求阶段（静态测试）**
开发还没写代码。
测试人员阅读需求文档、原型图，参加需求评审。
检查需求有没有模糊、冲突、遗漏。
> 属于**静态测试**，提前发现文档缺陷，减少后期返工。

2. **测试计划阶段**
编写《测试计划》：确定测试范围、环境、人员、工期、风险、测试类型（功能 / 性能 / 兼容等）

3. **测试设计阶段**
根据需求和原型，编写**测试用例**，评审用例。
> 这一步也是静态，不运行程序。

4. **开发编码 + 单元测试**
开发写代码，自己做**单元测试**（测单个函数，白盒）。
开发完成单个模块后，提交代码。

5. **集成测试阶段**
多个模块拼在一起，测试模块之间接口、数据传递。
版本提测后，**先做冒烟测试**，验证核心流程能不能跑通。
冒烟不通过，直接打回开发，不进入详细测试。
冒烟通过，执行集成测试用例；发现 bug 提交，开发修复后做**回归测试**。
集成测试大量依靠接口测试来完成。
多个后端模块拼在一起，模块之间大多通过接口通信，所以**集成阶段经常做接口测试**

- 集成测试：**模块之间交互**，除了接口，也包含内部函数调用（白盒集成，不用 http 接口）。
> 举例：同一个程序内部 A 函数调用 B 函数，两个代码模块集成，没有 HTTP 接口，这属于集成测试，但**不是接口测试**。
- 接口测试：专门测 API（http 接口等），接口可以是模块之间，也可以是系统和外部第三方系统之间（比如调用支付接口）。

***API：应用程序编程接口***
  1. API本质：API（接口）是一套调用规范，定义访问入口、请求参数、返回格式；后端业务代码是实现接口功能的程序，**不属于 API 定义本身，是接口背后的实现**。
   - 项目核心业务API：后端开发自研（登录、订单查询等）
   - 公共能力API：调用第三方现成API（短信、支付、地图）
  3. 从哪里调用API：
   ✔前端网页/APP
   ✔测试工具Postman/JMeter（接口测试）
   ✔后端其他服务模块
   ✔其他外部系统


6. **系统测试阶段（功能测试主要在这里）**
部署完整的软件到测试环境。
执行全部系统测试用例：功能、兼容性、易用性、弱网、安全、性能测试；
中间可以穿插**探索性测试**；
测出 bug 提交，开发修复，每轮修复都做**回归测试**。

7. **测试准出（测试总结）**
所有 bug 处理完毕，测试执行完成，编写测试报告，评估版本是否可以交付给用户验收。

8. **验收测试（UAT）**
业务方 / 客户在预上线环境，按照业务场景验收软件。
发现问题提交 bug，修复后回归。验收通过，准备上线。

9. **上线 & 线上回归**
版本部署到生产环境。
测试人员做线上简单冒烟验证，确认上线成功。
后续线上如果修复 bug，继续做回归测试。

### 归纳总结
软件测试
├─ **测试阶段（有先后顺序）**
│  ├─ 单元测试（开发，白盒，最小代码模块）
│  │  └─ 可执行活动：冒烟、回归测试
│  ├─ 集成测试（模块组合，模块间交互）
│  │  └─ 可执行活动：冒烟、回归、探索性测试
│  ├─ 系统测试（完整软件整体，黑盒为主）
│  │  ├─ 可执行活动：冒烟、回归、探索性测试
│  │  └─ 执行各类目标测试（功能、性能、兼容等）
│  └─ 验收测试UAT（业务/客户确认交付）
│     └─ 可执行活动：冒烟、回归测试
├─ **测试分类（多维度，可叠加到任意阶段）**
│  ├─ 按是否看源码
│  │  ├─ 黑盒测试：功能、兼容、弱网、易用、安全、性能
│  │  ├─ 白盒测试：单元测试、代码审计
│  │  └─ 灰盒测试：接口测试
│  ├─ 按是否运行程序
│  │  ├─ 静态测试：需求评审、代码审查、文档测试（不运行程序）
│  │  └─ 动态测试：功能、性能、兼容性等（运行程序）
│  └─ 按测试目标
│     ├─ 功能测试
│     └─ 非功能专项
│        ├─ 性能相关：性能、压力、容量、可靠性测试
│        ├─ 体验相关：兼容性、易用性、国际化本地化测试
│        └─ 其他专项：弱网、安全、容错、文档测试
└─ **通用测试活动（不属于独立阶段，全阶段可用）**
   ├─ 冒烟测试
   ├─ 回归测试
   └─ 探索性测试
